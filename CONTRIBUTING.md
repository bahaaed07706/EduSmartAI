# Contributing

Thanks for taking a look. This is a graduation project, but it is maintained to
the standard of something people would rely on.

## The one rule

**No change is "done" without evidence.** A test, command output, or a
screenshot. "It should work" is not a status. If you cannot show it working,
say so plainly in the pull request — an honest "unverified" is worth more than
an optimistic claim that turns out to be wrong.

## Before you start

Read [CLAUDE.md](CLAUDE.md). It carries the hard constraints, particularly the
data-preservation rules, and [docs/current-state.md](docs/current-state.md) for
what is verified right now.

## Setup

Python 3.12 and Node 24 — the versions matter. numpy 1.26.3 will not build on
Python 3.13+, and the lockfile was generated by npm 11, so an older npm resolves
a different tree and `npm ci` fails.

See the Quick start in [README.md](README.md).

## Running the checks

```bash
# Backend: tests and lint
cd backend
python -m pytest -q
python -m ruff check .

# Frontend: production build
cd edusmartai-frontend
CI=true npm run build
```

Accessibility and responsive audits need both servers running and credentials in
the environment — copy `scripts/.env.a11y.example` and fill it in locally:

```bash
node scripts/a11y-audit.js
node scripts/responsive-audit.js
```

Both exit non-zero on failure, so they work in a pipeline.

## Things that will get a change rejected

**Deleting academic data.** Users are deactivated, courses archived, enrolments
withdrawn. Anything with student history attached must refuse deletion with a
409 rather than dropping rows. This is not negotiable — the whole product
premise is that records survive.

**Re-seeding over an existing database.** `seed_data.py` is for fresh setups.

**A destructive migration.** Additive only: `ALTER TABLE ADD COLUMN`. Test twice
on a copy and verify row counts before and after.

**Committing a secret.** Including a demo password, including "just for
testing." Everything reads from the environment with no defaults.

**Role checks without ownership checks.** Being a lecturer is not permission to
read a course. Every resource endpoint resolves the actual relationship.

**Force pushing or rewriting history.**

## Writing tests

Add a test when it protects a real bug, a security boundary, a critical
workflow, or a deployment regression. Do not add tests to raise a count.

Every new endpoint needs a positive case and a negative authorization case. The
negative one is the one that matters: it is what proves a student cannot read
another student's data.

One thing worth internalising, from a real bug in this codebase: a test that
asserts a failure can hide a defect. `test_submission_download` asserted 404 for
an authorized caller because the fixture file did not exist — which meant it
passed while the download endpoint was completely broken on Linux. Assert the
success path with real data.

## Style

Match the surrounding code. Backend uses FastAPI dependency injection and
explicit Pydantic schemas; frontend uses the tokens and primitives in
[docs/design-system.md](docs/design-system.md) rather than new one-off styles.

Comments should explain *why*, especially where something looks odd. Several
places here have a non-obvious reason — Tailwind colours are literal hex because
`var()` breaks opacity modifiers, and character n-grams are used for retrieval
because the corpus is bilingual. Those comments exist so the next person does
not "fix" them.

## Pull requests

Describe what changed and why, list the evidence, and state any limitation you
did not resolve. If something is unverified, say which and what would verify it.
